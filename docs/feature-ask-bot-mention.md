# Фича: «Поиск в сети» (@-mention в любом чате)

Рабочее название в прототипе: **askBot** / «Поиск в сети».

## Активация

Фича может быть включена двумя путями:

1. **Вручную через мини-апп** — админ открывает карточку фичи и тапает тоггл. По умолчанию выключена.
2. **Автоматически** — если любой участник делает `@ChatLogixBot <вопрос>` в чате, где фича выключена:
   - бот всё равно отвечает (это единственный способ узнать, что фича нужна чату)
   - в чате выставляется флаг `active = true`
   - админ получает уведомление в DM: «в чате X включён Поиск в сети, потому что юзер сделал запрос. Отключить → ссылка».

**Админ может выключить** в любой момент через мини-апп. Если выключено — бот на `@mention` отвечает только короткой служебной строкой «фича отключена админом чата» (без расхода квоты).

Это даёт UX без жёсткой активации: фича сама себя «продаёт», когда нужна, но админ остаётся в контроле.

## 1. Суть фичи

Пользователь в любом Telegram-чате упоминает нашего бота через `@ChatLogixBot` и задаёт вопрос. Бот отвечает прямо в этот чат — **даже если он не добавлен в чат** (новое Telegram Bot API позволяет отвечать на mention без членства в чате).

Бот выступает «универсальным экспертом по запросу»:
- отвечает на технические вопросы
- поясняет фразы из переписки (через reply на чужое сообщение)
- разворачивает короткие реплики в подробный разбор
- **может искать актуальную информацию в интернете** (статьи, документация, новости) — если вопрос требует свежих данных

## 2. Триггеры активации и флоу

### Когда юзер делает `@ChatLogixBot <вопрос>`:

**Шаг 1 — бот отвечает уточняющим сообщением с inline-кнопками:**

Бот шлёт ответ **как reply** на сообщение юзера (его вопрос уже виден в цитате выше). Текст:

> Окей @username, где мне искать ответ?
>
> [🌐 В сети] [📚 В базе знаний чата]

Это сообщение **удаляется автоматически после выбора кнопки** (чтобы не засорять чат). Дальше бот шлёт уже сам ответ — отдельным сообщением, реплаем на исходный вопрос.

**Шаг 2 — поведение по контексту:**

| Состояние чата | Поведение |
|---|---|
| **База знаний включена** | Показываем обе кнопки. Юзер выбирает источник. |
| **База знаний выключена / чат без KB** | Кнопки **не показываем**. Сразу идём в web-search и отвечаем без шага 1. |
| **`@ChatLogixBot` без текста или шум** («привет», «ок», «спс») | Шлёт справку (текст ниже). Не считается за запрос. |

### Кейсы по типу запроса

| Триггер | Поведение бота |
|---|---|
| `@ChatLogixBot <вопрос>` без reply | См. шаги 1–2 выше |
| `@ChatLogixBot <вопрос>` + reply на сообщение | Контекст = reply-сообщение + вопрос. Кнопки источника аналогично шагам 1–2. |
| `@ChatLogixBot` без вопроса | Справка (текст ниже) |

### Текст справки (когда нет вопроса)

Бот отправляет в чат:

> Привет, @username 👋 Я @ChatLogixBot — помогу с ответом на вопрос прямо в этом чате.
>
> Как со мной общаться:
> • `@ChatLogixBot как работает webhook retry в TG?` — задайте вопрос напрямую
> • Сделайте reply на любое сообщение и напишите `@ChatLogixBot объясни` — разберу его в контексте
> • Я ищу в интернете или в базе знаний чата (если включена)

### Текст rate-limit-уведомлений (в чате, авто-удаление через 15 сек)

Отправляем прямо в чат как reply на запрос юзера, но **через 15 секунд бот сам удаляет сообщение** — чтобы не засорять чат.

При срабатывании per-minute лимита:

> ⏱ @username, слишком быстро. Подождите минуту перед следующим вопросом.

При срабатывании дневного лимита:

> ⏱ @username, на сегодня лимит запросов исчерпан. Завтра он сбросится — попробуйте снова.

## 3. Сценарии использования

### Сценарий A — reply на сообщение в чате
Один участник пишет техническое сообщение. Другой делает reply на это сообщение и пишет вопрос с @-mention.

**Пример запроса от юзера (как reply):**
> `@ChatLogixBot скажи что думаешь про это?`

**Ответ бота (после выбора «В сети»):**

> @ruslan, разобрал сообщение про webhook retry.
>
> Коротко: TG переотправляет update'ы до 24 часов, если webhook вернул не-2xx или таймаут (>10 сек). После 24 ч обновления **теряются безвозвратно**.
>
> 📖 Подробности (тапни «развернуть»):
> > • Retry-интервал: экспоненциальный backoff, начинается с ~1 сек, растёт до ~10 мин
> > • Параллельные retry не идут — TG ждёт ответа на текущий
> > • Если webhook отвалился совсем — переключитесь на `getUpdates` и пропустите дыру через `offset`
> > • Полезный приём: setWebhook с `drop_pending_updates=true` после длинного даунтайма
>
> 🔗 [core.telegram.org/bots/webhooks](https://core.telegram.org/bots/webhooks)

### Сценарий B — прямой вопрос без reply
**Пример запроса:**
> `@ChatLogixBot как работает webhook retry в Telegram?`

**Ответ бота:** аналогично сценарию A, но без цитирования.

### Сценарий C — продолжение диалога
Reply на сам ответ бота с уточнением.

**Пример запроса (reply на ответ бота):**
> `@ChatLogixBot а если webhook отвалился больше чем на 24 часа?`

**Ответ бота:**

> @ruslan, тогда update'ы за этот период **теряются** — TG их не сохранит дольше суток.
>
> Что делать:
> 1. Сразу после восстановления webhook вызовите `getUpdates` с большим `offset` — заберёте всё, что прилетело за последние секунды/минуты
> 2. Для критичных событий (платежи, подписки) держите **второй канал** — БД на стороне отправителя или периодический `getMe`-poll
>
> Восстановить «потерянные сутки» через Bot API нельзя.

### Сценарий D — вопрос с поиском по интернету
**Пример запроса:**
> `@ChatLogixBot найди свежие статьи про Bun 2.0 performance`

**Ответ бота (после выбора «В сети»):**

> @ruslan, нашёл 3 свежих материала по Bun 2.0 perf:
>
> 1. **Bun 2.0 release notes** — bundler в 2.3× быстрее vs 1.x, новый JS runtime parser
> 2. **Benchmark vs Node 22 / Deno 2** — HTTP throughput +18% к Node, SQLite-driver +60%
> 3. **Migration guide** — что ломается при переходе с 1.2
>
> 🔗 bun.sh/blog/bun-v2.0
> 🔗 dev.to/bun-vs-node-2026
> 🔗 bun.sh/docs/migration-v2

## 4. LLM-провайдер

Не привязываемся к одному вендору. Используем абстракцию через шлюз:

- **OpenRouter** — основной шлюз. Один API даёт доступ к OpenAI, Anthropic, Google, открытым моделям. Можно менять модель без рефакторинга кода.
- **Context7 MCP** — для запросов, где нужна свежая документация по библиотекам/фреймворкам.
- **Прямые SDK провайдеров (Anthropic / OpenAI)** — как fallback при деградации OpenRouter.

Базовая модель: **GPT-5 Mini** (быстрая, дешёвая, достаточная для технических Q&A).
Fallback для сложных вопросов: Claude Sonnet 4.6 или GPT-5 (полная).

## 5. Веб-поиск

Бот ищет статьи и свежие данные в интернете через **Brave Search API**:

- **Search endpoint**: $5.00 за 1 000 запросов = **$0.005 / запрос**
- Capacity: 50 запросов/сек
- **Бонус**: $5 free credits каждый месяц = первые **1 000 поисков/мес бесплатно**
- Возвращает URL'ы, тексты, новости — оптимизировано под LLM-контекст

Используем endpoint **Search** (не Answers) — свой LLM через OpenRouter стоит дешевле.

Поиск дёргается **на каждый web-запрос** (юзер явно выбрал кнопку «В сети» или KB не включена). При KB-поиске Brave не вызывается.

## 6. Расчёт стоимости (приблизительный)

Цены GPT-5 Mini через OpenRouter (на 2026-05):
- Input: ~$0.25 / 1M токенов
- Output: ~$2.00 / 1M токенов

Средний ответ:
- LLM: 1500 in + 500 out ≈ $0.0014
- Brave Search (если web-выбор): $0.005
- **Total с web-search: ~$0.0064 / ответ**
- **Total с KB-поиском: ~$0.0014 / ответ** (Brave не дёргается)

### Cost cap через rate-limit (а не квоты)

Чат-лимита **нет**. Защита от unbounded cost — **строгие rate-limits per user**:
- 1 req/min, 15/час, **50/день**

Максимум на одного юзера в день: 50 × $0.0064 = **$0.32 / юзер / день** (worst case, если все web).

Реалистичная средняя: чат с 100 активными юзерами, ~5% делают askBot в день, ~3 запроса/юзер/день, 50% web:
- ~15 web-запросов + ~15 KB-запросов в день = 15×$0.0064 + 15×$0.0014 = **$0.12 / чат / день** = **~$3.6 / чат / мес**

### Затраты при масштабе

| Активные чаты | Cost/мес (реалистичный) |
|---|---|
| 100 | ~$360 |
| 1 000 | ~$3 600 |
| 10 000 | ~$36 000 |

Если стоимость на чат вырастет неприемлемо — закручиваем per-user rate limit или вводим anti-abuse эвристики.

## 7. Лимиты

**Лимита на чат / на месяц НЕТ.** Никакой квоты, никаких пакетов докупки.

Защита от злоупотреблений — только **per-user rate limits**:
- **1 запрос в минуту**
- **не более 15 запросов в час**
- **не более 50 запросов в день**

Каждый счётчик отдельный, считается по `user_id`. Сбрасываются по соответствующему окну.

### Длина ответа
- Целевая видимая длина: **~1500 символов**
- Жёсткий потолок: **3000 символов**
- Длинная часть → **expandable quote** (нативный TG)
- Сплит на 2 сообщения **запрещён** — retry с инструкцией сжать

### Когда rate-limit сработал
Бот шлёт короткое сообщение в DM юзеру (не в чат, чтобы не флудить):

> Слишком быстро. Попробуйте ещё раз через минуту.

или для дневного:

> Сегодня вы уже использовали лимит запросов. Попробуйте завтра.

В чате при rate-limit — silent ignore (никаких сообщений, чтобы избежать спама в чате).

## 8. Формат ответа бота

Структура (целевая видимая длина **~1500 символов**, жёсткий потолок **3000**):
1. Приветствие с @-упоминанием автора вопроса (1 строка)
2. Короткий тезис / ответ по сути (2–4 строки)
3. **Подробный разбор в expandable quote** — TG-нативный «развернуть»
4. Если был web-search — ссылки на источники в конце (1–3 ссылки)

**Реклама / CTA в подвале — нет.** Бот не пытается ничего продать в чате. Чистый ответ, без призывов.

Сплит на 2 сообщения **запрещён**. Если итог > 3000 — модели уходит retry-prompt с инструкцией сжать.

## 9. Edge cases

- **Mention без вопроса** (`@ChatLogixBot` или `@ChatLogixBot привет`): бот не пытается угадать — шлёт короткое «не понял запрос, я умею X, Y, Z, задайте вопрос или сделайте reply + вопрос». Запрос не списывает квоту.
- **Короткие приветствия / шум** («ок», «спс», «лол»): аналогично — короткий справочник без расхода квоты.
- **Rate-limit сработал**: короткое сообщение в чате (reply на запрос), удаляется ботом через 15 сек.
- **Mention без прав на write в чате**: бот шлёт ответ в DM автору + короткое уведомление в чат.
- **Языки**: автоопределение языка вопроса, ответ на нём же.
- **Спам/abuse**: блок по user_id, повторяющиеся одинаковые mention'ы — silent ignore.
- **Очень длинный ответ**: длинная часть в expandable quote; жёсткий потолок 3000 символов, сплит запрещён — retry с инструкцией сжать.
- **Search не дал релевантных результатов**: модель отвечает по знаниям + явно говорит «свежих данных не нашёл».

## 10. Метрики

Все события — свои, минимально достаточный набор.

| Событие | Когда | Свойства |
|---|---|---|
| `askbot_chat_activated` | Первый раз фича сработала в чате — авто (через `@mention`) или ручной toggle в мини-апп. Один раз на чат. | `chat_id`, `chat_title`, `members`, `activation_source: 'auto_mention' \| 'manual_miniapp'` |
| `askbot_mention_received` | Бот получил `@ChatLogixBot <вопрос>` (до всех проверок) | `chat_id`, `user_id`, `has_reply_context: bool` |
| `askbot_source_chosen` | Юзер тапнул inline-кнопку выбора источника | `chat_id`, `user_id`, `source: 'web' \| 'kb'` |
| `askbot_answered` | Бот успешно ответил | `chat_id`, `user_id`, `source: 'web' \| 'kb'`, `response_chars`, `latency_ms` |
| `askbot_blocked` | Запрос заблокирован | `chat_id`, `user_id`, `reason: 'rate_minute' \| 'rate_hour' \| 'rate_day' \| 'disabled_by_admin' \| 'invalid_request'` |
| `askbot_disabled_by_admin` | Админ выключил фичу в мини-апп | `chat_id`, `user_id` (админа) |

### Воронка askBot

1. `askbot_chat_activated` — чат подключён
2. `askbot_mention_received` — DAU / WAU по chat_id
3. `askbot_source_chosen` — % web vs kb (если KB включена)
4. `askbot_answered` — успешные ответы (response_chars и latency как health-метрики)
5. `askbot_blocked` — топ-причины (rate-limit спайки, anti-abuse)
